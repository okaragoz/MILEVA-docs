Testing ​

Running the suite ​

The runner is a plain script, not a Pkg.test target:

bash
JULIA_NUM_THREADS=4 julia --project=. --heap-size-hint=3G tests/run_tests.jl

With 4 threads it takes four to five minutes and stays below 4 GB, and reports 1404 passing assertions, no failures and no errors.

Assertions per file, counted on one run with every file wrapped in its own test set (in-process group, blue) or from the summary table each subprocess prints (orange). The runner itself scores each subprocess file as one assertion on its exit code, which is why it reports 1404 rather than 1594; two subprocess files check by exit code only.

tests/run_tests.jl has two groups:

  • In-process files (test_files). The runner includes them one after another inside one @testset "MILEVA unit tests", in one Julia process and one namespace. The first file, test_grid.jl, does using Plots and include("include/mileva.jl"); most later files only do using Test and rely on that, so they run on their own only if you load MILEVA first (julia --project=. -e 'using Plots; include("include/mileva.jl"); include("tests/test_annulus_operator.jl")'). Files run in list order, so put a new file after anything it depends on.

  • Subprocess files (subprocess_files). These build their own dependency set instead of including include/mileva.jl, and re-including config/SimConfig.jl with a different set of definitions would redefine a struct, which Julia refuses. The runner launches each in a fresh julia --project process, streams its output, and records a failure if the exit code is non-zero.

Tests that write files put them under output/ (for example tests/test_2d_vcycle_scgs.jl writes its figure to output/tests/), which is git-ignored.

What a test should check ​

For an incompressible flow

∇⋅(2ηε˙)=η∇2v+2(∇η)⋅ε˙,

so a test run at constant viscosity cannot distinguish the two operators. Two rules for new tests follow from examples like this one:

  1. Test a property that the correct answer must have. The work-dissipation identity below holds for any Stokes solution at any viscosity field. Agreement between two solvers on one assembled matrix checks the solvers, not the matrix.

  2. Make sure the property responds to what you want to check. Rigid rotation has ε˙≡0, so the 2(∇η)⋅ε˙ term vanishes on it; the null-mode test is useful, but the viscosity-gradient term is checked by the work-dissipation identity at variable viscosity. Where it distinguishes truncation from inconsistency, require the error to shrink under refinement rather than sit below a fixed tolerance.

Tests and benchmarks ​

The suite guards identities. Agreement with published numbers is checked separately, for the 2-D spherical annulus, by benchmarks/hernlund_tackley_annulus.jl against Hernlund and Tackley (2008) and the annulus column of Fleury et al. (2024); see Benchmarks and verification.

Adding a test ​

  1. Create tests/test_<topic>.jl. Everything in include/mileva.jl is already in scope when the runner reaches it; to make it runnable on its own as well, guard the load:
julia
using Test
if !isdefined(Main, :SimConfig)
    using Plots; gr()
    include(joinpath(@__DIR__, "..", "include", "mileva.jl"))
end

Add it to test_files in tests/run_tests.jl with a one-line comment saying what property it defends. A file that builds its own include set goes in subprocess_files instead and must exit non-zero on failure.

  1. Build configurations from SimConfig() plus field overrides, never positionally, and use cfg.geometry = "spherical_annulus" for anything 2-D. A planetary configuration that a test needs lives in tests/fixtures/ (for example tests/fixtures/Venus_BMO.jl).

  2. Keep it small: a few seconds, coarse grids, no output beyond output/tests/. Coarse is fine for an identity (Nu = 1, W/D=1, energy closure); it is not fine for a claim about a resolved physical state.

  3. Prefer an identity, a conservation law or an exact solution to a golden number. When you compare against a stored value, store the reason with it and expect to update it.

  4. Vary the input that the property depends on: a viscosity test needs a varying viscosity, an energy test a heat source.

  5. Check that the new test fails on code it is meant to protect against (for example by reverting the change locally and running it).
